# Scope and limitations

## Interaction model

Version 0.21 uses visible Goodnotes Web controls in an isolated headless browser. It does not call private save endpoints, decode native Goodnotes files, export cookies or manipulate Windows app caches. The UI can change independently. This is experimental software, not an official Goodnotes API. Most controls currently expect English labels. Account/plan features and future Web layouts may differ.

## Reading and handwriting

- PDF exports are snapshots. Reads by exportId remain tied to that snapshot; refresh or export again for current content.
- Some Goodnotes exports contain almost no usable text, including visible typed text. This occurred in the live board test. Local OCR and page images provide a fallback.
- OCR is approximate, especially for handwriting, umlauts, formulas, tables, small text and colored backgrounds. A search miss does not prove absence. English/German models are bundled; recognition runs locally.
- Native handwriting recognition uses Goodnotes' conversion preview, then cancels. Only genuine ink strokes support this path. Scans and template backgrounds do not become editable ink.
- Summarization is performed by the calling assistant from returned pages, not by a separate server-side AI service.
- PDF processing is limited to 150 MB, 2,000 pages and three million extracted characters. OCR processes at most ten pages per call. Large documents can exceed a client's timeout.
- PDF is not a lossless native Goodnotes backup.

## Writing and formatting

- Existing documents require an exact local URL/title permission. Explicitly created documents and duplicates are authorized automatically; verified renames update the binding.
- Range edits check preceding text and formatting. Supported formatting is bold, italic, underline, strike, six-digit text color, font size, paragraph alignment, HTTP(S) links and whole-field flat bullet/numbered/none lists. Offsets use UTF-16 and are end-exclusive. Nested lists and embedded rich objects are rejected.
- A planned edit can apply up to 20 nonoverlapping `formatRanges` to the final text in one verified save. Body/heading formatting can share this operation; box backgrounds, images and object moves remain separate verified operations. Planning reduces repeated UI work but does not make a board update atomic.
- Full-field replacement may change mixed formatting. Prefer range edits for local changes. One HTTP(S) link spanning a simple text field was tested live, including editing an existing link. Complex lists, multiple overlapping link ranges and unusual structures are not covered by live tests.
- A blank point may open an empty editor during a read. These calls are marked as non-read-only UI operations.
- Objects are selected visually, not by stable backend IDs. Overlapping items, blue artwork, off-screen handles, locked objects and large groups can prevent safe selection. Keep selections fully visible and inspect the preview.
- Text boxes support width resizing; height follows content. Goodnotes may constrain other aspect ratios. Mismatches are reported as uncertainty after the attempted edit.
- Native snapping can adjust movement slightly. Object results include the requested and observed bounds; pixel-perfect positioning is not promised.
- Native rectangle, ellipse, triangle, diamond and rounded-rectangle creation uses the current native style. Single point-selected native shapes expose fill opacity in steps of 10 percent and stroke thickness (0.10 to 2.00 mm); zero opacity disables fill, positive opacity enables it using the existing color. Exact unreachable slider values stop with uncertainty. Shape stroke patterns, arbitrary vertex editing, and rotation are not exposed. Native shape labels can be read and edited with expectedKind: shape, selecting the border of unfilled shapes; exact text and rich formatting are checked after reload. This does not expose shape vertex or connection editing. Ink/connector calls can configure native pen/pencil/highlighter, pen kind, supported thickness and custom color. These settings persist in the isolated profile. Selection and text colors support native custom inputs when exposed. Font families are not implemented. Flat list and highlight operations cover the whole field; highlights use Goodnotes' native 50% opacity. Low-level planned board grids do not resize, pack or prevent overlap; the dedicated learning-board planner separately measures and packs its managed cards. Current-viewport text queries do not automatically search the whole board.
- Handwriting conversion replaces selected strokes with typed text. Recognition and conversion are separate calls so text can be checked or corrected first.
- Native page copy and single editable text/sticky/image copy are supported with saved verification checkpoints. Image copy requires the exact source-pixel hash and crop read from the native preview. Single text/sticky/image moves from whiteboards or notebook pages use a source PDF, verified copy, visual reacquisition and source deletion; failures can leave two copies. Rectangular lasso selections can be copied natively between documents using a captured source appearance and saved-paste checkpoint. This visual path does not certify exact text, hidden object properties or object counts; use the text/image-specific tools for their stronger content checks. Source selections must remain on one page, with numeric zoom and enough destination space. Different backgrounds, overlapping destination artwork or rendering differences can leave an uncertain copy. Atomic cross-document move and persistent group/ungroup are not implemented. Lasso-based transformations do not create a persistent group.
- Front/back commands use the native menu; there is no numerical layer index to verify. Non-overlapping objects can look unchanged. Sticky collapse/expansion and position locks use separate guarded flows because their normal selection disappears. Expansion of an arbitrary previously collapsed sticky without an MCP checkpoint is not exposed.
- Documents can be moved to Trash and recovered using a verified MCP trash receipt. Pages deleted by this MCP from 0.7 onward have a pre-delete PDF and native-order checkpoint and can be recovered if remaining page contents/order are unchanged. Recovery of an uncertain deletion requires the saved checkpoint and independently checks the current state; it does not relabel the old receipt. Permanent deletion/emptying, arbitrary historical Trash recovery, folder Trash/recovery, sharing, comments, audio, marketplace purchases, freehand image cropping and direct editing of background PDF objects are not exposed.
- Rectangular image cropping saves original pixels privately, then verifies the cropped source pixels and appearance after reload. Goodnotes can destructively replace the image source; a later crop cannot reveal removed content. The local original can be explicitly reimported, but there is no automatic in-place rollback.
- Text-box styles support native colors, corner radius, border width, padding and shadow only where Goodnotes exposes the native menu. Whiteboards without it return `supported: false`; batches stop before a style write. This does not add font-family selection, arbitrary preset management, sticky styling or independent shape border/fill colors.
- Folder rename/move requires a separate exact path/title permission. It checks immediate child identities and titles, not every nested document's contents. A structural manifest is saved; this is not a content backup. Moving folders changes saved item paths, so refresh the library index afterward. Duplicate destination names are rejected. Existing folder permissions are independent of document-content permissions.
- Templates are limited to the currently visible size/color catalog. Page-template verification preserves page identities, exported text and the applied appearance across reload; this does not certify every hidden/native object property. Native template menus can be unavailable on some pages. No Apply is replayed after an uncertain write.

## Index, batches and pages

Library refresh is bounded and resumable. Scroll-aware collection reads recycled cards exposed by the Web UI, up to 10,000 per folder and 12 folder levels; truncation is reported. Page enumeration is capped at 2,000. Virtualized fixtures cover recycled rows, but no live library/notebook at these maximum sizes was tested. Long-distance page drags may fail when the target is outside the mounted sidebar. Known edits invalidate matching snapshots. Visible date hints and a maximum age reduce repeated exports but cannot guarantee detection of remote content changes. Force a new refresh when current contents matter. Local OCR can be queued for pages with almost no text; OCR still cannot prove completeness.

Board scans cover an explicit region of at most 9 by 9 viewports, with up to three new tiles per call. A completed region is not an exhaustive infinite-board index. OCR misses drawings and some handwriting. Saved visual locations require unchanged content and a reachable view; notebook locations also bind native page identity/dimensions and tolerate bounded rendering variation; they are not stable native object IDs. Moving/recoloring/hiding part of an object may intentionally invalidate a saved location.

Batch plans and learning materials persist private text in the local data directory. Batches are sequential, not transactional. Explicit references may use only typed outputs of earlier verified steps. Read-only backup failures can resume; dispatched operations with uncertain status stop. Only an explicit rejected/no-write receipt permits the separate safe-retry operation. Explicitly skipping a step does not undo it. Default backups are PDFs, not lossless native documents. Native snapshots use separate Goodnotes copies and PDF baselines; keep the snapshot copy unchanged. Restore creates another new document, never an in-place rollback. Comparisons use rendered pages up to 1000 pixels and cannot prove hidden metadata or all editing semantics.

Page management verifies native page identities and order after reload. It refuses incomplete sidebars and deletion of the last page. Rotation is verified using exported page dimensions, so square pages are rejected. Outline creation checks its visible title after reload. Flat native outline listing/rename/delete also checks exposed entry identities, titles, page bindings and native page order. Nested/imported outline editing is unsupported. Thumbnail loading is excluded from the conflict hash. Metadata checkpoints are not automatic rollback. Uploaded PDFs become new editable notebooks, but background PDF graphics do not become individual Goodnotes objects. Image insertion accepts PNG/JPEG up to 20 MB and 40 million pixels and uses Goodnotes' default size/position; transform the returned selection when needed.

Learning bundles contain assistant-supplied summaries, tasks and cards. The server does not invent them, check factual accuracy, post tasks elsewhere or import cards into Anki. PDF compilation preserves selected page order but does not guarantee native ink editability, interactive forms, all outlines or cross-document link behavior.

## Verification and recovery

Whiteboard reload checks restore the captured native page identity, zoom and pan for text creation/replacement/formatting, image insertion and object creation/transforms. PDF export also preserves this view, including default batch backups. Restoration is bounded and fails closed when the page changes or its original camera cannot be reached. These fixes do not certify every other operation or arbitrary coordinate-based batches across external navigation/restarts; use saved object targets when resuming from a different view.

Read/search automatically recognize up to three pages with no PDF text per call, using local OCR. `ocrIfMissing: false` disables that work; `maxOcrPages` sets a 0–10 page budget. Results identify processed, pending, failed and low-confidence pages; searches mark incomplete coverage and visual review needs. A result below 65 confidence triggers one higher-resolution adaptive pass, retaining the higher-confidence result. This threshold is a heuristic, not an accuracy guarantee. OCR is approximate, cached against the export snapshot, and does not add a searchable layer to the original PDF. Existing cached OCR is retained; explicitly refresh the export or rerun OCR with replacement when needed. Pages with partial native text may still contain unrecognized images or handwriting; manually requested OCR remains available. Goodnotes can shrink a large board into a low-resolution PDF; a completed OCR pass does not imply every label is readable.

Text operations compare text/formatting after reload. Object operations check visible bounds or appearance and save private before/after images. New-object appearance checks compare unselected content in both directions, allowing two pixels of rasterization variation and local antialiasing; a hard mismatch limit prevents large blank areas from masking a missing stroke. New sticky text is additionally checked as exact text. Each receipt names its actual verification. This is not a transaction, guaranteed rollback, cloud acknowledgement or proof of iPad delivery; the browser may reload from local cache.

Notebook contents can appear seconds after the toolbar/page surface. New-object appearance verification makes bounded read-only attempts while content arrives, without repeating creation. New-text verification maps actual character positions to the native page and repeats a bounded blank read without reinserting text. Visual selection can repeat up to three selection-only attempts with a fresh baseline when content is still arriving; it never repeats edits or paste. Other operations can conservatively report a failed/unconfirmed check during slow loading; an empty early preview is not proof that the page is empty.

Concurrent remote editing cannot be locked. Handles expire after ten minutes and are invalidated by server navigation. Cancellation stops later input where possible; input already sent may remain. Pending/uncertain receipts block automatic replay. Inspect the result instead of inventing a new operation ID to force a retry.

## Validation

Version 0.18 avoids repeated network-idle waits within one loaded document and restores whiteboards with integral wheel inputs. A missing native text-box style menu gets one read-only reload and reacquisition; the recovery compares unselected appearance, exact text/formatting and geometry, so different selection handles cannot be mistaken for changed content. A genuinely absent menu still reports unsupported. Timings vary with Goodnotes loading, document size and connection; a four-card comparison is not a guarantee for building a full learning board from lecture files.

Current validation and measured results are recorded in [VALIDATION.md](VALIDATION.md). The reported automated results come from local runs; see the validation record for hosted-CI status. Development failures and uncertain operations remain in the private journal; a later independent verification does not rewrite their status. Colored ball-pen, highlighter, pencil, fountain-pen and brush-pen lines passed. Earlier short arrowheads did not satisfy strict path coverage and remain uncertain. A later diagonal arrow passed with separate head strokes, denser pointer samples and final-point settling; this is not exhaustive coverage of all arrow lengths and pen settings.

Automated tests cover the real MCP transport, locks/receipts, text conflicts, Unicode/multiline edits, formatting/link preservation, PDF extraction/search/rendering, OCR, selection detection, covered zoom controls, both native color palettes, resumed indexing, stale snapshots, batch crash recovery, page-order calculations and learning/PDF outputs. Browser tests use a synthetic local fixture; they do not prove compatibility with every account, document or OS.

Live tests on November 9, 2026 use dedicated test documents only. The real stdio MCP connection passed typed-text and native-sticky reads, full replacement and range edits, sticky/rectangle/ellipse/ink creation, object duplication/movement/deletion/resizing, and corrected native handwriting conversion. Saved text, formatting or visual results were checked after reload. Library creation, document duplication/rename/move, PDF export, local OCR and text formatting also passed live controller checks. Handwriting recognition remains approximate: one synthetic ink example needed a correction before conversion. Failed/uncertain development receipts remain unchanged; they are not relabeled as successful.

Version 0.3 live controller checks additionally passed PDF import; page duplication, deletion, addition, rotation and outline creation; a two-step board layout resumed in separate processes with PDF backups; OCR-based editable target selection; new text, PNG insertion, linked text/alignment, sticky color and an ink arrow. Indexing resumed with per-page OCR, found content in both a notebook and a board, and refreshed a known modified snapshot while reusing the unchanged notebook. A compiled PDF was rendered and visually checked in the requested BETA/ALPHA order. The real stdio connection discovered all 42 tools and verified page moves in both directions, add-before and deletion with the initial page identities/order restored. It also read cached library results, completed batch status and saved receipts, and produced a learning bundle. These are specific synthetic examples, not exhaustive coverage of every palette, PDF or object type.

Windows/Chrome is live-tested; macOS/Linux are not. Normal results are compact JSON; images are returned only on request. [Compact mode](COMPACT.md) has a measured smaller tool-discovery response; total token savings have not been measured.

The real MCP connection also passed cached document search/read/rendering, zoom out and back in, and Web connectivity reporting. No iPad delivery was inferred from these checks.

## Managed learning-board revisions (0.20)

The dedicated revision workflow requires saved checkpoints from a completed learning-board build, revision or selected-object adoption. It changes selected cards, makes bounded moves and appends sections. Changed selected content and visible occupied destinations stop the operation. White backgrounds and independently recognized native light-gray dots are supported; invisible objects, remote concurrency and unchanged off-screen contents are not exhaustively checked. Updates cannot outgrow reserved card slots, moves must fit one guarded viewport, and boards are limited to 12,000 layout pixels. Flexible one-to-three-column layouts support spans, sections and up to 24 cards/12 original figures per ordinary layout. See [STUDY-REVISIONS.md](STUDY-REVISIONS.md).

## Adoption and linked collections (0.21)

Older boards can be copied and selected native text boxes/images adopted without rewriting the board. This does not discover every object or make handwriting, shapes or sticky notes managed cards. Source page references are caller-supplied. Selected objects must be fully visible, separated and within the documented size bounds. The final PDF comparison proves the adoption copy stayed unchanged; it is not a lossless native backup or a guarantee against simultaneous remote edits.

Collections split caller-supplied materials by measured space/object limits, not by automatically understanding a lecture. Original figure/caption groups stay together; the assistant should provide meaningful sections and review the learning sequence. Overview and neighbor links use native HTTP(S) text formatting with exact destination checks. Each child has its own durable workflow and verification. Execution is not atomic, and a stopped run can leave partial/empty boards. See [STUDY-COLLECTIONS.md](STUDY-COLLECTIONS.md).
